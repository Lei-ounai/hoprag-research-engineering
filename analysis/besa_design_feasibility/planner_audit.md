# Query Need Planner 可行性审计

## 问题样本与隔离

从现有 `answerable_dev` 分割选 35 道真实题。按问题类型和标注事实数分为 7 个实际存在的分层，每层 5 道。分层只用于抽样。每层按 `SHA-256("42:" + Query ID)` 排序后取样，便于复现。这个等额样本覆盖了少数分层，比例不代表完整 451 题分布。

`planner_probe.py prepare` 单独读取现有划分和分层字段，导出仅含 `query_id`、`question` 的 `planner_inputs.jsonl`。随后 `plan` 阶段从这个文件生成 `planner_outputs.jsonl`，严格校验字段，分解函数只收到问题文本。Query ID 仅写回用于对齐。规划过程不加载原始数据集、Gold、答案、题型、语料、排名或候选文档，不调用网络或模型。生成输出后才读取 Gold 并逐题人工检查。`planner_eval.jsonl` 与 `planner_manual_ratings.txt` 独立保存这次审计的金标映射和判定。数值置信度来自规则的固定启发式，未做概率校准。

| 问题类型 | 证据数分层及样本数 | 人工判定可用 | 分解缺陷 | 回到原始问题 |
| --- | --- | ---: | ---: | ---: |
| Comparison | 2 条 5 题、3 条 5 题 | 5 | 3 | 2 |
| Inference | 2、3、4 条各 5 题 | 6 | 6 | 3 |
| Temporal | 2、3 条各 5 题 | 3 | 2 | 5 |
| 总计 | 35 | 14 | 11 | 10 |

## 分解规则和审查口径

规则识别题面中的并列谓词、来源归属、日期和时间比较词。每个需要给出 `need_id`、`need_text`、`need_role`、`depends_on`、`confidence`。能通过形式检查时，生成 2–4 项，显式比较问题可以生成一个依赖来源项的 `join`。该项表示比较或联合判断，后续文档双编码或 Jina 逐对评分只应接收实际可检索的内容需要。格式识别失败或约束数不合理时，输出单项原始问题与低置信标志。

人工阅读检查题面主要约束、关系、来源限制和依赖是否保留。14/35 可用，其中 2 题对应题面约束但存在额外背景 Gold 未映射。12/35 同时可用并映射全部标注事实。8 条有缺陷的计划也能把所有 Gold 大致映射到某个片段，说明「能对上 Gold」本身无法证明原子性或独立可检索性。风险标签可以重合。7 题出现多个约束归到一个需要，5 题出现过度拆分，4 题有片段内指代，2 题丢失来源或时间范围，1 题遗漏独立检索需要，1 题生成错误比较操作。另有 5 题的部分 Gold 与题面显式约束对齐较弱，其中也包括已经失败的计划。完整数据见 `planner_eval.jsonl`。

| 案例 | 具体行为 |
| --- | --- |
| `q-1407` | 产生两个独立条件，先匹配 TechCrunch 的反垄断指控，再匹配 The Verge 报道的苹果对搜索引擎有效备选的判断。原规则没有发明公司答案。 |
| `q-1492` | 保留两篇不同媒体的点球报道，并用依赖两条来源需要的节点比较发布时间。 |
| `q-1787` | 保留三条不同报道约束，两条含 `she`。独立评分前需要仅从问题把指代恢复为 Taylor Swift。 |
| `q-1799` | 错误拆开 `NBA betting sites and apps`，把日期与来源主题分离。 |
| `q-2270` | 两个体育报道命题保持分离，错误把比赛内部的 `after` 解读为文章发布时间顺序。 |
| `q-1693` | 把第三篇报道的未来计划放进比较操作，缺少该来源对应的独立检索项。 |
| `q-0221` | 两个指定日期的 Sporting News 报道都保留。第三条 Gold 来自不同媒体，提供伤病背景，题面未单列为条件。 |

这份审查只有一名标注者。题目重复涉及少数新闻事件，规则和人工结果均未在保留集验证。

## 五道可继续测量的问题

以下是从已审计样本手选的语义可用问题，用于检查候选原子需要逐对打分能否运行和成本是否可控，样本刻意偏向清楚的句法结构。冻结抽样结果不受这次手选影响。`planner_eval.jsonl` 给出了事后配对的 Gold 证据和文档 ID，输入仍只用题面。

| Query ID | 可检索需要 | 理解限制 |
| --- | ---: | --- |
| `q-1400` | 2 | 必须保留各自公司和财务指标，“同一期间”由联合判断处理 |
| `q-1787` | 3 | 评分前从题面显式展开 Taylor Swift 的代词 |
| `q-1407` | 2 | 两条公司条件需要归于同一公司 |
| `q-1648` | 2 | 区分放款条件报道与检方动机指控 |
| `q-1492` | 2 | 时间顺序是检索后根据两个报道判断，不单独做文档匹配 |

**本轮结论**　提取少量清楚的来源条件可行。该临时规则的成功率不足以直接为正式 BESA 系统提供稳定的结构化输入。若进入下一轮，建议将校验前置，只有当计划保留题面显式来源、日期、主体，且每条需要可独立检索时才运行需要级评分。若依赖关系不明确、分解丢掉约束或输出超出预算，使用原问题与现有检索排序。当前固定置信分本身挡不住表内的错误。

## 重现命令

在正式项目根目录通过原有虚拟环境运行。`prepare` 与 `plan` 可分两次调用，以核验分解阶段接收的资料边界。

```powershell
& .\.venv\Scripts\python.exe -B -m analysis.besa_design_feasibility.planner_probe prepare
& .\.venv\Scripts\python.exe -B -m analysis.besa_design_feasibility.planner_probe plan
& .\.venv\Scripts\python.exe -B -m analysis.besa_design_feasibility.audit_planner
```
