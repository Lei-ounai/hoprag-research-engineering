# HopRAG BESA-v0 开发集实验报告

## 决策

采用 30 对评分预算的 C-B30 在 451 道开发题上比 P5-B 多找齐 3 道，完整证据覆盖@10 从 333/451（73.84%）升至 336/451（74.50%），差值按未舍入数据计算为 **+0.67 个百分点**。3 道收益均来自用于选配置的 Tune。在 180 道内部 Validation 题上，两者均为 132/180（73.33%），Evidence Recall@10 也相同。本轮完成了可运行的开发实验，当前结果不足以支持进入 1,804 道保留题的正式验证。

## 实现与边界

| 模块 | 实际输入与产物 |
|---|---|
| [experiment.py](experiment.py) | 复用既有 QueryPool、Candidate、Chunk 和第六轮开发 ID。加载冻结 P5 候选及其历史 Jina 顺序，用 RRF 与 Jina 2:1 重现完整 P5-B 排序，逐题校验历史 Top 10。451 题候选池含 15–29 篇唯一父文档，平均 21.42 篇。 |
| [planner.py](planner.py) | 仅接收原问题字符串，生成 2–4 条带 ID、角色、依赖和规则置信度的检索需求。比较或先后判断保留为操作元数据。接受同时要求结构和题面约束可检查，confidence 是规则值，尚未校准。 |
| [scoring.py](scoring.py) 与 [run.py](run.py) | 利用原问题与 Chunk 的缓存 BGE-M3 相似度、Need 的词项 IDF 匹配和 P5-B 先验，按 Need 和父文档分配评分机会。按 90 对上限生成一次有序计划，截取 30/60/90 的稳定前缀。对同一 Need、同一父文档取最佳已评分 Chunk，输出原始分数、支持值、Chunk ID 和缓存来源。独立 SQLite 保存评分与逐题断点。 |
| [selector.py](selector.py) 与 [pipeline.py](pipeline.py) | 读父文档、原始排序、评分和缓存向量，返回最多 10 篇唯一父文档、完整排序、每步边际贡献和回退原因。拒绝计划、评分或缓存异常、超硬上限及无效选择触发完整 P5-B 回退。并列按 P5-B 原名次、父文档 ID 决定。 |
| [evaluate.py](evaluate.py) | 独立离线适配器，复用 [hoprag/evaluation.py](../../hoprag/evaluation.py) 的来源级指标。按题型、事实数、Planner 接受情况分别汇总，附保留分块的文本诊断。 |

Need 内各父文档用竞争名次计算分位值。支持值等于分位值乘以 $1-\exp(-\max(s-\tau,0))$，其中 $s$ 为 Jina 原始分数，$\tau$ 为 Tune 门槛。分数未过门槛时支持为 0，未评分的父文档继续按原先验竞争，不计负分。P5-B 先验为按候选池长度缩放的倒数名次。各 Need 等权，加入文档只增加此前已覆盖最大支持值之上的部分。

A 重放 P5-B。B 以 0.75 权重使用 P5-B 先验并按父文档向量余弦做 MMR。C 只加入 Need 边际覆盖。D 在 C 之上限制为同一媒体来源、同一已支持 Need、胜出 Chunk 余弦至少 0.90、词三元组 Jaccard 至少 0.80、数字和否定标记一致，且任一 Need 的新增支持不超过 0.05，才扣近重复分。E 在 D 上固定 P5-B 第一篇。桥接权重为 0。本轮实现证据集合选择，其联合覆盖分数不用于判断文档之间是否具有推理关系。

### Gold 隔离与评价

评分及重放入口从冻结开发 ID、原问题及已有候选与向量构造输入。正式选择接口不接收答案、必需事实、标注题型或证据来源。离线评价可读取标注，在原始数据读入后仅取本轮 451 道开发题，由评估端计算结果并做分组。Gold 不决定回退、Need 或分块次序。测试给选取接口传入禁止访问标注字段的对象，并检验非开发题 ID 在入口被拒绝。

Top 10 始终指 10 篇唯一父文档。正式 Complete Evidence Coverage@10 要求所有标注事实均有对应来源命中。Evidence Recall@10 先逐题计算命中事实比例再对题目平均。同一父文档可贡献不同事实，相同的来源和归一化事实对去重。本轮全部标注事实均有已解析来源。额外分块诊断采用原评估器的字面归一化，移除普通空格与换行，保留大小写及标点。标注片段必须完整落在同一个保留分块内，匹配不到也可能是分块边界、截断或转述。诊断无法确认一条证据可支持答案或多跳关系。

## 开发实验

沿用原 451 个开发 ID，以 SHA-256 对固定前缀 42 和 Query ID 排序，分成 271 道 Tune 和 180 道内部 Validation。[划分清单](run/development_split.json)已保存。Tune 搜索 C/D/E 共 135 套组合。以完整题数、较少回退、较少评分对数、预算和稳定配置 ID 依次选择，冻结后才比较 Validation。全开发集曾参与历史 P5-B 策略选择，此处用于描述性对齐。

各预算均以门槛 0.0、先验权重 0.75、Need 权重 0.25 胜出对应 Tune 组。D/E 的重复权重为 0.10。最终选中 C-B30，其重复权重为 0。[Tune 网格](run/tune_grid.csv) · [冻结配置](run/tune_freeze.json)

### 实测成本

- Windows 项目环境为 Python 3.14.8。复用 Jina Turbo INT8 ONNX CPU，4 线程、批大小 16、256 tokens，模型摘要和提交号存于性能文件。B90 实际累计模型推理约 304.2 秒，累计评分墙钟 325.54 秒（含首批 pilot）。
- 首批 20 道 Tune 题有 4 道接受，356 个评分对全部为新推理。冷跑全进程 17.24 秒，评分阶段 12.76 秒。暖跑命中同一批 356 对，新增推理 0，分数、分块及三档支持值一致。暖跑全进程 4.11 秒，评分阶段 0.028 秒。
- 全开发评分进程从 20 题的断点继续，墙钟 320.48 秒，CPU 累计 1,207.41 秒，峰值工作集约 615 MiB。三个评分进程墙钟合计约 341.83 秒。评分阶段从启动 2 小时预算计时到完整落盘约 6 分 51 秒，包含早期输入适配修正。续次离线评估 22.30 秒，三个评分进程与这次评估合计约 364.13 秒的实测进程时间。历时记录按进程统计，开发分轮之间的人为间隔未计入。
- B30/B60 的推理量和推理时间从共享的真实评分前缀统计。阶段墙钟的均值/P95 为前缀推理、共享预筛及缓存开销与选择开销的估算，各档未单独冷跑。全开发评分共生成 9,063 个独立缓存键，另外 293 次来自本轮独立缓存。本轮 Need 文本未命中早期精确评分键。历史 Jina 排序用于 P5-B，历史 Jina 缓存按只读方式查询。

## 研究结论

1. **是否超过 P5-B？** 全开发描述性结果多 3 道，内部 Validation 完整覆盖与 Evidence Recall 均持平。
2. **是否集中在少数题型？** 2 道推断、1 道比较，全部是 Tune 恢复。2、3、4 条事实的题各 1 道。样本不足以确认某类问题获得稳定提升。
3. **是否带来过多回退？** C-B30 的 333 道原完整题均保持完整。MMR 在相同预算下回退 48 道，说明直接提高全篇多样性会损伤任务所需的事实覆盖。
4. **哪档最划算？** B30。B90 相比 B30 的实际新增推理量约为 3 倍，完整题收益为 0。更高预算主要改善哪些候选块被评分。
5. **是否继续研究桥接核验？** 值得做小规模离线标注与消融。先验证明确的来源、主体和时间关系能否区分有证据的关系与实体共现，现有排序保持桥接权重 0。应先修正规划器的来源范围与复杂指代问题，并检查 Jina 实际输入中是否保留关键事实。
6. **是否进入 1,804 道保留题？** 暂缓。当前收益全部来自调参子集，且推断和关系核验的收益尚未得到独立验证。此次保留题没有运行 BESA。
